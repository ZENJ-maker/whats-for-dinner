# 今晚吃啥 · What's for Dinner

**把你会的菜和冰箱里现有的食材记下来，自动算出今天能做什么；选择困难时转个盘；想换口味时，让 AI 用你手上的食材生成没做过的菜谱。**

一个纯前端的手机端 Web 应用。没有后端、没有账号、没有数据库服务——所有数据留在你自己的浏览器里，可以直接托管在 GitHub Pages 上。

---

## 它解决什么问题

每天最难的问题不是「怎么做菜」，而是「做什么」。

- 你会做的菜不少，但一到饭点就想不起来；
- 冰箱里有东西，但看不出它们能凑成什么；
- 想尝试新菜，不知道用现有食材能做成什么。

这个应用把这三件事分别变成：**菜品库**、**食材匹配**、**AI 生成**。

## 功能

| 模块 | 说明 |
|---|---|
| 菜品库 | 录入自己会做的菜：封面照片（拍照或选图，自动压缩）、菜名、主料、调料、时长、难度、做法步骤。照片在上、菜名在下的卡片式展示。 |
| 食材库 | 记录家里现有的食材，支持一次输入多个、快捷添加常用项。 |
| 按食材点菜 | 首页列出所有菜品，按「主料命中率」算出匹配度：100% 即现在就能做，否则告诉你还差哪几样。四档排序：优先消耗 / 匹配度 / 时间 / 难度。 |
| 转盘抽菜 | 点「抽一道」进入独立的转盘页面，从当前筛选结果里等概率抽一道，转盘动画结束后弹出结果卡，一键记为「今晚吃这个」。 |
| AI 生成菜谱 | 以现有食材为输入，批量生成没做过的菜谱，结构化输出（菜名/时长/难度/食材/步骤/口味），可单条或全部导入菜品库。支持「换个新口味」和「配一桌」两种模式。 |
| 备份 | 菜品、食材、照片导出为一个 JSON 文件；换设备或清缓存前可恢复。 |

## 界面

三个主要页面：

1. **点菜首页** —— 顶部是「我的冰箱」食材条，下面是排序 tab 和菜品列表，每条显示封面、菜名、时长难度、能用上的食材和匹配度。底部是「🎲 抽一道」按钮。
2. **转盘页** —— 环形排列的菜品缩略图 + 菜名，指针固定在 12 点，转盘旋转 5 圈后停在结果上，弹出结果卡。
3. **AI 厨房** —— 显示当前食材与模型配置状态，三个生成入口，结果以卡片流展示。

## 部署到 GitHub Pages

1. 把仓库推到 GitHub；
2. 仓库 **Settings → Pages → Build and deployment → Source** 选 **GitHub Actions**；
3. 推到 `main` 分支即可，`.github/workflows/deploy.yml` 会自动跑测试、构建并发布。

构建的 `base` 是 `'./'`（相对路径），所以**仓库名可以随便取**，不需要改任何配置。应用用的是 Hash 路由，刷新子页面不会 404。

## AI 部分

### 为什么这里值得用大模型

「根据食材推荐菜」如果用规则做，只能匹配到已知的菜谱库；而用户真正想要的是**他不知道的、但用现有食材能做的菜**。这是一个开放生成问题，规则表覆盖不了，必须靠模型的世界知识。

但真正需要工程处理的是另一件事：**模型自由发挥的文字，没法变成应用里的数据。**

### 怎么让输出能用

1. **结构化输出**：请求时要求 `response_format: json_object`，返回后用 Zod 校验字段（菜名长度、时长范围、难度枚举、步骤条数）。任何一项不合格就整批拒绝。
2. **失败重试一次**：只在「格式不对」时重试，并在重试的 prompt 里附上错误提示；网络和鉴权错误不重试，避免浪费额度。
3. **入库前不信任模型**：生成的菜先展示、可编辑，确认后才写进菜品库，并标记 `source: 'ai'`，和自己的菜区分开。
4. **结果缓存**：按「食材集合 + 已有菜名 + 模型 + 数量 + prompt 版本」做 SHA-256，命中即复用，默认 7 天过期。
5. **演示模式**：没配置 API key 时返回内置示例菜谱，线上 demo 永远点得动——作品集最怕的是点开链接就报错。

### 配置

设置页填入 Base URL / Model / API Key，预置了 DeepSeek 和 OpenAI 的选项。任何 OpenAI 兼容接口都能用。

> ⚠️ key 保存在浏览器 localStorage。这只适合个人 demo；生产环境应该由后端代理转发，不要把密钥下发到前端。

## 技术栈

Vite 7 · React 19 · TypeScript · Tailwind CSS v4 · Zustand · IndexedDB（idb）· Zod · Vitest

## 架构

```
src/
  pages/        页面：Home / Spin / Dishes / Pantry / AiKitchen / Settings
  components/   DishCard、DishForm、Sheet、PhotoPicker、BottomNav…
  stores/       Zustand：菜品与食材（持久化）、AI 配置与生成状态
  lib/          db(IndexedDB) / match(匹配) / sort(排序) / wheel(转盘角度) / image(压缩) / name(归一化)
  ai/           client(调用) / prompt(提示词) / schema(Zod 校验) / cache(缓存) / mock(演示数据)
```

数据流：

```
食材库 ──┐
         ├─→ normalizeList 归一化 ─→ matchAll 计算 coverage ─→ sortMatches ─→ 首页列表
菜品库 ──┘                                                              └─→ 转盘候选集

食材 + 已有菜名 + 口味画像 ─→ buildPrompt ─→ 模型 ─→ extractJson ─→ Zod 校验 ─→ 结果卡片 ─→ 导入菜品库
```

关键设计取舍：

- **匹配在纯函数里**：`normalizeName` / `matchDish` / `winnerIndex` 都不依赖 React 和 DOM，可以直接单测，也方便以后搬到服务端。
- **照片不进 localStorage**：localStorage 只有 5MB，照片走 IndexedDB 存 Blob，展示时生成 objectURL 并在卸载时 revoke。
- **归一化放在录入时**：菜品主料存的就是归一化后的词，匹配时只做集合运算，不需要每次重新解析。

## 测试

```bash
npm run test
```

覆盖的是容易错、且错了不容易发现的地方：

- 食材别名归一化（西红柿→番茄、嫩豆腐→豆腐）与各种输入格式；
- 匹配覆盖率、缺料文案；
- 四档排序的稳定性；
- 转盘角度与中奖下标的互逆关系（含跨圈、压在分隔线上等边界）；
- AI 输出的 Zod 校验、从带解释文字的回答里提取 JSON；
- 缓存 key 的一致性（食材顺序无关、模型或模式变化要换 key）。

## 已知限制

- 单用户、单设备。数据在浏览器里，换设备要靠导出导入。
- 食材不记数量，`优先消耗` 用「能消耗的食材种类数」近似。
- 菜品封面由用户上传，不做 AI 生图。
- 转盘最多显示 12 道菜，多出来的只能在列表里看——再多就挤成一团了。
